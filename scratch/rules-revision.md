## 背景

核对 `AGENTS.md` 与 `screenlab-rules.md`，发现三处矛盾：① 通知后是否停；② 是否主动推进下一步；
③ 裁决权归属。判断：多为"层没分开"，非真对立。

**分层原则（本轮共识）**：方向（做什么、开哪条线）归 YZ；执行（已定工作单内部怎么走）归目标。

## 一、通知 —— 已定（2026-09-26）

**结论**

- 通知 = **单向告知**（fire-and-forget），**不与"停 / 继续"绑定**。"停不停"的判据是
  "有没有卡在需要 YZ 判断的地方"，与"发没发通知"无因果关系。
- 原 `AGENTS.md` 把两个不同动作塞进一句，须拆开：
  - **告知**：报阶段性成果 -> 发完即走，无控制含义。
  - **升级 / 求助**：遇到需人介入的问题 -> 向 YZ 发出请求。**升级本身 ≠ 停**——同批还有未阻塞的事就继续做；
    只有**全部**剩余工作都阻塞在该请求上时才停（见下「唯一停条件」）。
- **"该不该通知"不立通则**：它随模式变（交互会话 YZ 在场=噪声；无人值守才需要），
  是"该判断"而非"该立规矩"的东西。

**拟改点**

- `AGENTS.md` `## 指令`：删除「通知人：…然后停下等人」整条；只保留**方法 + 对象**：
  `tools/feishu_notify.py`、默认发 YZ、含双引号时走文件 + stdin。
- `AGENTS.md`：「遇到需人介入 -> 停」改为「升级不必然停」，归入**控制 / 裁决**一组
  （与"目标推不出才升级""全部阻塞才停"同组）。
- `screenlab-rules.md`：`每完成一步 -> 通知` 降级为 **里程碑 / 需拍板时通知**；
  保留"不等回复、立即下一步"（其真意 = **通知不发控制流**）。

**开放**：撤掉"何时通知"后是否仍要一条默认？YZ 倾向：不立。

## 二、停 / 继续的判定 —— 已定（2026-09-26）

**根因**：「该不该停」被问成了**价值 / 形势判断**题——会话在里面，有沉没成本与"显得在推进"的动机、
看不到自己边界 -> 自评不准。

**结论**

- **主手段 = 前置判据，把判断题降级为查表题（治本）**：判据在冷静时（讨论中、YZ 参与）定，
  等于对当下动机的预防性约束（判据源外移）。
- **工作项轻量 schema、增量声明**（反对提前画全图：既贵又脆，图是边跑边长出来的）：
  - `depends_on`：YZ 决定 / 另一平台 / 外部事件；
  - `stop_condition`：何为做完、何为阻塞；
  - 溯源：能否挂到 `§0.0` 某句。
  - 决策机械：**项可跑 ⟺ 依赖已满足；停 ⟺ 无可跑项（或仅剩带作废 / 不可逆风险的项）**。
  - "值得做"去主观：**挂不上 `§0.0` 的活 = 新方向，归 YZ**，不作为续命工作。
- **唯一停条件**：`停 ⟺ 无可跑项`。两个警示：
  - **作废 / 不可逆风险**：升级的问题可能让在做事作废（方向被推翻），或后续动作不可逆
    （提交 / 推送 / 部署 / 花钱）-> 该分支停、必要时整体停，即便还有"不阻塞"的活。
  - **"不阻塞" ≠ "值得做"**：别拿"还能干点啥"续命空转；剩余活价值边缘时直接停（对齐 rules 防失控上限）。
- **subagent = 带判据的反方检查（补丁，非裁决者）**：只在里程碑用，给它工作单 + 判据，
  钢人化论证"停 / 继续"以抓自我合理化；补判据覆盖不到的残余（作废 / 不可逆风险、是否续命空转）。
  **结论仍归固定判据**；subagent 换会话再判同类问题，不提供外部参照，不能当 oracle。
- 若两者都要靠 -> 判据没定好，回去补工作单，不是加 subagent。

**拟改点**

- `screenlab-rules.md`：工作项模板加 `depends_on` / `stop_condition` / `§0.0` 溯源；
  "全部阻塞才停"与"唯一停条件"对齐；保留防失控上限。
- `AGENTS.md`：确认"停"的定义 = 无可跑项（非"需人介入即停"）。

## 三、主动推进 / 方向变更 —— 已定（2026-09-26）

**判据 = 是否偏离已定目标 / 任务**

- **目标内 + 达成该目标的合理方案 -> 直接推进**：**记录 + 及时通知**，然后继续；不事前逐条请示。
- **明显转向 -> 先讨论（YZ）**。
  - "转向" = 改变目标本身，或推翻已定前提 / 范围 / 结论；
  - "方案" = 同一目标的不同做法；二者以"**是否仍服务同一个已定目标**"区分。
  - **"明显"的门槛**：拿不准是方案还是转向时，默认当转向（先讨论）。
- 依据（YZ）：造方向不禁止，但**必须带 why**；明显转向要讨论，围绕目标的合理方案可直接做（见 §二、§四）。

**新任务（目标外 / 明显转向）：kilo 可提议，等 YZ 确认**

- kilo **可以提出新任务**——**大目标 YZ 与 kilo 都清楚**，故 kilo 有参照能生成"挂在大目标上"的提议（why 先于方向）。
- 提议 = "先讨论"的一种由 kilo 主导的形式：写明**卡在哪 / 服务大目标哪一句 / why**，**等 YZ 确认再做**。
- **等确认 ≠ 全局停**：有其它可跑项就继续做（§一 / §二）；全阻塞才停。

**推进有度（不无限漂移）**

- 工作以**任务**为单位：**先讨论出一个任务，再做这个任务**。
- 因此推进被**任务边界**天然限定：任务内自治推进；任务完成 -> 回到讨论，**不自动接下一摊**。
- **任务边界 = 审计点**；不靠"信任"，靠边界。

**护栏 = 记录 + 通知（不是事前批准）**

- 自治的可追溯性与可质询性由"记录 + 及时通知"提供，YZ 可事后否决。
- 呼应 §一：通知是告知、不发控制流。

## 四、裁决权归属 —— 已定（并入 §三）

- "裁决者是目标，不是 YZ" 的口号**只在目标内部成立**：目标内的执行裁决归执行者（方案自决）。
- **目标本身的设定与变更归 YZ**（明显转向先讨论）；故 YZ 是**目标层的裁决者、执行层的质询方**。
- 落地措辞：`screenlab-rules.md` 的"裁决者是目标，不是 YZ"改为
  "**目标内裁决归目标；目标变更 / 明显转向归 YZ**"。

## 五、规则的 scope 与来源 —— 已定（2026-09-26）

**第一维 = scope（决定落点 / 归属）**

- **跨任务**（任何会话成立）-> `AGENTS.md`
- **任务型**（只做那类任务时需要）-> 任务规则（`rules/`，见 §七）。**任务方法不进 AGENTS.md**。
- **事故补丁**（为某次事故打的）-> 就地，**标注事故编号 + 可退休性**，到期复核删除。

**来源标签**（规则为何存在）

- **不变量**（硬约束，如 secrets 不入库）
- **事故补丁**（某次踩坑）
- **倾向纠偏**（模型训练出的系统性默认，见 §六）——因倾向是**全局的**，纠偏型天然属**跨任务层**。

**已定的 scope 归属**

- **验收**：通用原则不是"别自证 e2e"，而是**面向使用**——以**真实使用者的完整使用路径
  （含边界 / 失败 / 异常）**为参照，不只是 happy path 顺不顺。归**任务型**，不进 `AGENTS.md`。
- **commit**：无"授权"问题。**默认自主，规则限权**——有规则按规则，无规则按判断，除非有明确禁令。
  约束只保留在**不可逆 / 外溢**处（secrets、force-push / 改写历史 / 发布 / 共享主分支）。
  （现 harness 默认"只在被要求时才提交"是面向陌生仓库的安全默认，**不适用于 dev 语境**。）
- **图不进上下文**：为 #61 打的**事故补丁**，留任务侧；底下可推广的"上下文卫生"暂不升格（防过度工程）。
- **edit 最小锚点**：**删**——属工具操作细节，非协作纪律；写进规则无价值且僵化。

## 六、模型倾向 -> 纠偏型规则 —— 已定（2026-09-26）

**判断**：倾向 = **系统性偏差**（可预测、非随机），规则是纠偏的正确工具（纠偏型归跨任务层）。

  - 7 迎合（软化分歧、倾向认同）—— `待定 A3`：先论证再认同。

  - 11 维护既有结论 / 产物（沉没成本，不轻易推翻）—— `待定 A4`。
  - 12 报喜不报忧、把动作包装成成果 —— `待定 A5`。

  - 13 信息囤积（什么都往上下文塞）—— `已纠`：上下文卫生。

3. **只留少数高杠杆**，防规则泛滥挤占判断。

## 七、任务规则的加载 —— 已定（2026-09-26）

**原则：加载优先用显式指针（人给或工作单带），自动 / 匹配只是便捷退化。** 显式优于隐式——因为可核对。

**形态**：平文件 + `rules/` 目录 + YZ 指定（**不做 skill**）

```
locus/
  AGENTS.md        # 跨任务条文 + 一条约定："任务规则在 rules/，按名加载"
  rules/
    README.md      # 索引：名字 / 适用场景 / 加载时机
    screenlab.md   # = 现 screenlab-rules.md
    coding.md      # 编码任务通用（验收面向使用等）
    handoff.md     # 交接 / 无人值守
```

- 放 `locus/rules/`，**不放代码仓**（规则是"AI 怎么干活"，且 `cogos/AGENTS.md` 已写"开发约定见 locus"）。
- **`rules/README.md` 索引是关键**：没有它，"指定"要靠记文件名。
- 命名固定（`screenlab.md` / `coding.md` / `handoff.md`），不用日期 / 编号漂移。

**约定（写进 `AGENTS.md`）**

> 任务规则在 `rules/`；**任务前由 YZ 指定加载**（可多条）；加载 = 读文件，**读完复述确认**。
> 任务明显需要而 YZ 未指定时，**先问加载哪条**，别猜。无人值守由**工作单 / 交接首句携带规则名**。

**为何不用 skill**：skill 索引常驻 system prompt（稳），但**触发仍靠模型判断**（软）；我们要的正是
**显式触发**，skill 的自动匹配用不上，只剩格式负担。索引文件补上"发现性"即可。

**边界**：此档依赖**有人给指针**（交互 = YZ；无人值守 = 工作单首句），故"首句带规则名"须与本节一起定死。

## 八、checkpoint / scratch —— 已定（2026-09-26，同日按 E 二次修订）

**结论**：`CHECKPOINT.md` 与 `scratch/` 合并为**一条规则**——它们本是一套，被"躲 `/undo`"的要求拆成三处（根规则 + scratch 锚点 + 仓外正文）。

- **两层**：`scratch/` = **任务内工作 / 交接缓冲**（locus 内、入库防丢，短命）；记忆层（`current.md` + `entries/`）= **唯一持久**，只存结论。
- **收口（顺序不可倒）**：结论（**含 why + 被否方案**）进记忆层 → 证据类转存 → **删草稿**。**过程默认不留**（原"`git mv` 进 `projects/<工程>/checkpoint/` 归档"作废）。
- **`projects/<工程>/checkpoint/`**：降为历史 / 证据层，规则不再主动写；已有内容保留、不重写。
- **搬回仓内**：`snapshot:false` 下 `/undo` 只回退消息、不回退文件 → 原"落在 `/undo` 之外"的唯一理由消失；留在仓外只剩坏处（不在 `active.md`/`index.md` 视野、无版本、无备份）。
- **规则形态**：规则与数据分离——规则一份（`rules/memory.md`），`scratch/` 只当活数据；不再有"锚点指向别处"。
- **前提（基石，待验证）**：`snapshot:false` 下 `/undo` 不回退任何文件（含已跟踪）。若重启 snapshot，`scratch/` 会被回退，届时再评估，不默认搬回仓外。
- **落点**：`locus/rules/memory.md` + `rules/README.md` + `scratch/README.md`；删 `CHECKPOINT.md`、`scratch/checkpoint-rule.md`；讨论文件迁入 `locus/scratch/`。
