# Token 消耗分析

> 日期 2026-08-14。分析对象：cogos 联调会话（`26/08/14-cogos-联调与开发-1`）token 101K。归因 + 解决方案。

## 现象

cogos Phase C 联调 3 bug 修复会话，token 101K。大头不是"修复"本身，而是**反复全文读源码 + 大段 edit 往返 + 冗长中文输出**。

## 归因

### 构成估算

| 来源 | 规模 | 估算 token | 说明 |
|---|---|---|---|
| 源码全文读入 | ~150KB（含重复） | ~40K | 两轮各读一遍，占大头 |
| 其中重复读浪费 | ~35KB | ~10K | core.py×2、config.py×2、bs_provider.py×2 |
| edit 的 oldString 往返 | ~30KB | ~8K | 大段函数重写，新旧两版都又算一遍 |
| assistant 中文分析输出 | — | ~15-20K | 每阶段几百到上千字总结 |
| 测试/grep 输出 | — | ~5K | 全量 pytest 377 用例输出 |
| 系统固定开销 | — | ~20K | system prompt + 工具 schema + 历史记忆 |

### 量化依据

被读的 feishu 模块源码共 **3114 行 / 约 117KB**，逐文件字节数：

| 文件 | 字节 |
|---|---|
| session.py | 21.6K |
| bs_provider.py | 20.8K |
| accounts.py | 18.1K |
| core.py | 13.4K |
| test_bs_card.py | 11.1K |
| bs_card.py | 8.1K |
| config.py | 5.8K |
| daemon.py | 5.2K |
| test_provider.py | 4.5K |
| 其余小文件 | ~9K |

### 四条根因

1. **定位与开改是两轮独立全文读**：第一阶段读 `bs_provider/bs_card/core/bs_setup/bs_workspace` ≈62KB，第二阶段"一起修改"又读 `handler/daemon/accounts/session/bs_cmd/测试文件` ≈64KB，两轮几乎不重叠，等于把整个 feishu 模块灌进上下文。
2. **重复读已读过的文件**：core.py（13.4K）×2、config.py（5.8K）×2、bs_provider.py（20.8K）×2，纯浪费约 10K。
3. **大段 edit 替换**：`setup_provider` 整函数（40 行→100 行）一次替换，bs_card.py 被 edit 5 次、bs_provider.py 5 次、test_bs_card.py 2 次。每次 oldString 精确匹配大段原文，等于旧代码再读一遍、新代码再写一遍。
4. **分析输出偏长**：每个阶段都给几百到上千字的总结/说明，而非直接结论。

## 解决方案

### 总览

| 改进方向 | 方案 |
|---|---|
| ① 定位/探索分级读 | 方案 B：subagent 隔离 + 记忆提取 |
| ② 读完记下，修改时不重读 | 方案 A：代码心智模型记忆 |
| ③ 大文件探索/大改动丢 subagent | 方案 B：读丢写留 |
| ④ edit 最小锚点、拆小步 | 方案 C：最小锚点 edit |
| ⑤ 输出归宿 | 方案 D：分析落盘 + 清单式总结 |
| ⑥ 减单价（正交轴） | 方案 E：模型路由（便宜模型委派） |

### 方案 A：代码心智模型记忆（解决重复读）

"重复读源码"的解法是"读完记在脑子里"：把代码的心智模型持久化，跨会话复用，替代每次全文重读。

**三个层次**

1. **工程印象**（locus 已有）：工程是啥、讨论到哪、遗留坑 → current.md + entries/
2. **代码心智模型**（要补）：模块职责、调用关系、数据流、不变量、易错点、入口/测试命令
3. **代码本体**（留工程仓库）：真正的源码

**难点**

- **stale**：代码会变，行号/签名过时。
- **记什么**：只记不变量 + 易错点，不记流水账。
- **token 悖论**：记忆必须比"重读代码"便宜才有意义 → 压缩到原文 1/10 以下，只存指针不存副本。

**落地形态**

"代码认知地图"：模块清单+职责、数据流、不变量/易错点、入口+测试命令。每条是指针不是内容。位置倾向工程本体 `docs/`（同生命周期），locus 只留指针。

**一致性维护**

放弃"记 commit + 判断 HEAD 变了就重新核对"——过度触发，99% commit 不影响心智模型。改为两个动作触发：

1. **写时同步**：agent 改代码 → 收尾同步更新地图条目（主路径，改动时信息最准）。需固化成明确约定，不能靠自觉。
2. **读时对照**：读代码 → 发现与记忆矛盾 → 就地更新（兜底，覆盖"别人改的"）。矛盾本身就是失效信号，不需版本号。

版本号降级为参考注解（"大致对应 08-14 状态"），不作触发机制。漏网风险：改了忘同步 + 从此不读那块 → 过时但无害，可接受。

### 方案 B：subagent 隔离 + 记忆提取（解决探索式阅读贵）

探索式阅读（第一次理解陌生模块，需全文读）省不掉、不该硬省，解法是丢给 subagent——中间过程不进主会话，省 token。

但隔离省 token 与"做事形成理解"是同一枚硬币两面：隔离掉的中间过程里恰好藏着新理解。解法不是二选一，而是让 subagent 在**收尾时把理解压缩成摘要带回来**。

**机制**

- **记忆提取发生在 subagent 内部**，不是主会话事后猜。subagent 上下文信息最全的时刻就是它做完事的瞬间。
- 任务指令里**强制一个"理解摘要"收尾动作**（固定格式），几 KB，落进代码地图 entry；中间过程（读了哪、grep 了什么、怎么想的）不进主会话——那是流水账。
- 摘要格式：模块职责（一句话）、关键数据流/调用链、不变量/易错点、我改了什么为什么、还遗留什么不确定。

**边界**

只对"产出结构性理解"的任务提取（探索/改代码）；一次性查询（"某字段在哪定义"）不记，记了是垃圾。

**读丢、写留（③ 并入）**

③"大文件探索/大改动丢 subagent"并入本方案，不单独成条。统一规则：需理解全貌才能安全动手 → 丢 subagent；只改一处 → 主会话 read 片段 + edit。

- 触发阈值不用行数硬卡，判据是"改这里会不会牵动别处"。
- **读丢**：探索（读）丢 subagent。
- **写留**：改动（写）留主会话——改代码需主会话持有一致的上下文和决策权；subagent 改完回来还要 review + 可能返工。只有整块独立重构才值得整块丢 subagent。

### 方案 C：最小锚点 edit（解决大段 edit 往返）

- **最小唯一锚点**：oldString 只贴"改动行 + 前后各一行上下文"，够唯一即可，不贴整函数。唯一性靠上下文锚定，不靠贴大段。
- **大改动拆小步**：一次大替换拆成多个内聚的小 edit（先改签名 → 再改一处逻辑 → 再改调用处），每个 oldString 短。
- **平衡**：拆太碎 edit 次数多、每次有固定开销，粒度 = "一步一个内聚变更 + 锚点唯一"，不是越碎越好。
- **刚性边界**：整函数重写时 oldString 必须覆盖整个旧函数体才能删中间，省不掉。这类改动重新审视是否丢 subagent（呼应③）。

### 方案 D：输出归宿（解决输出冗长 + 分析不沉淀）

- **动作后总结 → 清单式**：改了哪几个文件（各一行）、验证结果（一行）、遗留（一行），不复述 diff。
- **分析类输出 → 落盘成文档**：对一个问题的分析写进文档（locus entries / 工程 docs）。下次想了解先看已有分析，信息不够才重新完整分析——分析是一次投资，不是一次性消耗，即使增加一点 token 也值得。
- 与代码记忆同源：做事形成记忆/资产，不随会话上下文消失。

### 复利式优化（记忆反哺读代码）

读代码成本从"每次 O(全文)"降到"首次 O(全文) + 之后 O(片段)"：

- 第一次进模块：探索式全文读（贵），产出地图（一次投资）
- 之后：先读地图 → 直接知道读哪、甚至跳过 grep → 片段读（便宜）

**② 是 ① 的前置**：没有地图，① 的"片段读"是瞎猜，还得靠全文读兜底。**摘要质量决定复利效率**：记忆写得敷衍（只有文件清单、没有不变量），之后仍得重读，复利落空。

### 方案 E：模型路由（减单价，正交轴）

四方案 A–D 减的是 **token 数量**；本方案减的是**单价**——把便宜模型能胜任的任务委派给绑定便宜模型的 subagent。两者相乘，非二选一。机制复用方案 B 的 subagent 通道：同一件事既隔离中间过程（省数量）又用便宜模型（省单价）。

**任务分级**

| 任务类型 | 便宜模型？ | 理由 |
|---|---|---|
| A 只读定位：grep / 找文件 / "某字段在哪定义" / 列清单 | ✅ 最合适 | 只读、输出可校验、量大（40K 大头正是"读"） |
| B 机械改写：改名 / 格式化 / 搬文件 / boilerplate | ⚠️ 可用需 review | 可能引入细微错误 |
| C 理解判断：推断不变量 / 判"改这会不会牵动别处" / 方案权衡 | ❌ 必须好模型 | 核心价值所在 |
| D 摘要提取：写认知地图不变量 / 易错点 | ❌ 必须好模型 | 复利前提（见方案 A/B） |

**红线**：D 类绝不下放——摘要质量决定方案 A/B 复利，是整套方案最大失效点；便宜模型理解力弱会漏不变量 → 地图变空壳 → 复利落空。

便宜模型的正确位置是 A 类只读定位：负责**降低搜索空间**（找文件、罗列事实、给位置），好模型在缩小后的空间上只读关键片段做理解决策。契合"读丢写留"：读（探索）丢便宜 subagent，写 + 提炼不变量留主会话用好模型。

**技术落点**：`.kilo/agent/*.md` 的 `model:` 覆盖，定义 `explore-cheap` 等 agent，按任务类型路由。

**遗留**：候选模型价格比待查（便宜几倍能否覆盖返工 + subagent 重复读冗余）；落地时机推迟。
