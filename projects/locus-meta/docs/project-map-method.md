## 为什么「代码认知地图」不够

方案 A 落地的「代码认知地图」= 模块清单+职责、数据流、不变量/易错点、入口+测试命令。两个真实失效点：

- **从文件名 + 旧文档猜**：`entry.py` 被猜成「入口」，实为消息数据模型。不理解项目目的，就归不对组。
- **自造标签**：地图写「通信线」，项目自己无此概念，作者都说不出指什么。

根因：地图的基准是代码，但**代码只是「已实现的子集」**。设计文档里未实现/被放弃的部分、以及代码「为什么存在、想干什么」，纯代码图都丢；而调试的前提恰恰是知道这些。

## 项目认知地图 = 目的优先 + 状态轴

建立在对「项目目的 + 设计」的完整理解上，代码作为已实现子集落到图上。

### 可复用骨架（八节）

1. 项目目的（认知层）——为什么存在、想干什么
2. 概念体系——项目自己的语言，先于代码读
3. 接口（设计目标，可标「未实现」）
4. 关键不变量（带兑现状态）
5. 状态轴总览——✅ 已实现 / 🔧 调试中 / ⏳ 未实现 / ⚠️ 折中待核
6. 代码分层——目的树下的代码子集，G1..Gn
7. 模块 ↔ 不变量映射
8. 已裁决 / 折中 / 待核

### 建图过程（样本 = cogos）

口述背景 → 设计文档核对 → 偏差清单 → 人工审核裁决 → 读代码核验 → 成图。

- 口述/文档会错，代码核验修正：消息落地目录、bitable 表数、device 与 bs-bot、agent 与 agent-bot。
- 裁决交人：编排/数据职责切分、数量限制、编号分类。
- 折中/待核留人判，不擅断。

## 三条原则

1. **完整理解 ≠ 完整复制**：图是理解的骨架 + 分层 + 指针，细节留本体文档；树型 + 按需加载解决规模。
2. **维护是循环问题**：AI 触发更新 + 人纠偏；写时同步（改动改变不变量/易错点/状态轴才重写对应小节）+ 读时对照。地图废掉是因为没有维护循环，不是因为大。
3. **验收分工**：AI 逐条验形式（可交 subagent，只报形式层面达标/红线，不报「通过」）+ 人通读验实质（拿代码记忆对照易错点）。
