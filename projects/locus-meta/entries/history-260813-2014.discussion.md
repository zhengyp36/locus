# 活跃讨论空间

> 单元式讨论的上下文空间。文件是 source of truth，聊天是草稿。
> 用法：每讨论完一个单元 → /save 存档 → 人 /new 清空 → /load 加载结论 → 继续下一单元。

## 主题：人与 AI 协作方法论

## 单元 1：单元式讨论方法（本方法本身）

- 以单元为基本讨论粒度；人把握单元边界（单元把握归人）；一次只讨论一个单元。
- 循环：/save 存档（总结落盘）→ 人 /new 清空 → /load 加载结论 → 继续下一单元。文件=磁盘、聊天=内存。
- 本质：手动补"执行/调节层"；"摩擦有利"——边界显式判断是特性而非缺陷。
- 存档必须先于回退（先写盘再清内存，否则结论丢失）。
- 回退用 /new（清空到最初）；/undo 只回退上一条消息，不回退磁盘文件。
- 只有 /save + /load 两条命令，无 checkpoint（合并命令跳过 reset，方法价值全在 reset）。
- /load 契约：读取存档到上下文，不解读、不判断、不推进、等指令。
- 文件结构：主题（前置、写一次）+ 单元 1..N。
- 姿态 vs 动作：四条常驻规则（文件是 truth / 单元把握归人 / 摩擦有利 / 每次一单元）放 /load 种子；动作放 /save。
- 新/历史单元判定：无明确说明 → 新单元；明确说明（如"重新讨论单元 1"）→ 写对应单元；不存在 → 报错。
- 总结忠实转述会话结论，不评价、不加观点、不存过程。
- 实现约束：save/load 跑主上下文（subagent 隔离不可行——仍加载 AGENTS.md 且看不到对话），命令体保持极简。

## 单元 2：模式的命名

- 模式的内涵 = 偏置（唯一内容）。
- 输出形态 = 模式达到的效果；隔离上下文 = 落地副作用；两者都不属于模式。
- 关键区分：偏置是"量"（连续可调的实质），模式是"档位"（总结出的、命名的、可复用、可切换的偏置设置）。
- 命名结论：保留"模式"，定义钉死为"偏置档位"。
  - 显性指向偏置用限定式"偏置模式"。
  - 复合词用"×式"：发散式 / 聚焦式 / 批判式 / 执行式。
- 暂不造新词；等定义稳定、成为 CogOS 一等支柱时，再考虑专名（候选：态 / 档 / 相）。

## 单元 3：模式的种类与收敛（五档；与 Kilo agent 的关系）

- 收敛方法：用"场景"收敛，不用"轴"收敛。轴是连续谱（发散↔收敛中间有无数点），只用于收敛后审计、不用于生成档位；档位由"真实走偏场景 + 偏置真不同"切出。
- 收敛判据（两条同时满足才立一个模式）：① 偏置真不同（排除输出形态差异，如"解释""翻译"）；② 对应一个反复出现、AI 会走偏的 locus 真实场景。
- 收敛结果：五档（人已认可）：
  - 发散——求多求新、不上限——讨论早期找方向
  - 收敛——求深求结论——#2 思考过长（收敛档即缺的"调节层"）
  - 质疑——人给的=候选、主动找漏——独立视角（规则 3）+ 防回声
  - 执行——边界给定、纯运算——#1 条件式规则失效里的"确定范围执行"
  - 转述——忠实、不加观点——#3 无法复用 + /save 存档
  - 砍掉：澄清并入收敛（偏置差异不够大）；解释并入执行（只是形态差异）。
- 与 Kilo 内置 agent 的关系：
  - 自定义 agent 不"放弃"内置 agent——两者共存于 /agents，仅同名覆盖才替换；default_agent 只改默认。
  - 两者正交两轴：五档 = 偏置轴（怎么想）；Kilo 内置（code/ask/debug/orchestrator plan）= 任务轴（干什么）。不 1:1 映射、不合并成一个清单，是相乘关系（如"收敛"偏置 + debug 任务）。
  - 命名撞车：Kilo 的"模式"实为 primary agent（`mode: primary` = 可作主 agent 切换），与"模式=偏置档位"是两回事。
  - 查漏补缺姿势：先立五档偏置轴（自定义 agent 写 system prompt + AGENTS.md 底座），再单独审任务轴（locus 是否需要 code/debug 的任务方法）。
  - 会遗漏的只有"任务方法"（如 debug 的定位→修复工作流），对 locus（讨论/记录/写 markdown，不写代码）几乎无关；真正风险是"混轴"，不是遗漏。

## 单元 4：模式的实现与工程组织（收敛到：塑形极简）

- 实现方式：用 Kilo agent 承载模式（agent.md = 注入偏置的 system prompt）；五档大而全被质疑，改为"场景驱动、先做能用的、实践中补充"，不做整体设计。
- 多工程组织：三工程——locus（元工程/协作方法论）、~/codex/cogos（agent 项目）、~/codex/agent-study（理论）。
  - locus_original 的 AGENTS.md 问题：位置绑定（Kilo 按目录只加载一份）；内容混装（人格/机制/流程塞一份）；"projects.md 约定字段手动加载"是脆弱的条件式规则。
  - Kilo 原生分层：AGENTS.md = 常驻底座；agent（primary）= 切换层；skill = 按需层。工程约定不常驻、进 agent；projects.md 退化为路由索引。
- 内置 agent 查证：code/ask/debug/orchestrator/plan 编译进 kilo 二进制（`native: true`），非磁盘 .md；源码在 opencode `packages/opencode/src/agent/`。内置偏置 = 权限（permission）为主 + 极简话术为辅；code 和 plan 无 system prompt、纯靠权限。用户可写 `.kilo/agent/<name>.md` 覆盖同名内置 agent。
- 收敛结论：塑形被高估。拆两类——结构（文件契约、交接协议、权限）＝硬，保留且极简；话术（人格、态度、偏置档位）＝软，砍掉或降级为待检验。
  - AGENTS.md 砍到只剩记忆契约（文件是什么、/save /load 怎么用、单元边界归人）。
  - 模式/agent/五档降级为未检验假设，等真实场景反复走偏再针对性加一条极简规则。
  - 记忆管理协议本身也要尽量薄。
- 一句话：塑形只留结构、砍掉话术；记忆是唯一硬通货，管理协议要薄。
