# 认知地图思路修订（阶段 2 反思）

> 2026-08-14。来源：阶段 2 冷启动（方案 b）执行后的反思讨论。

## 背景

阶段 2 方案 b 冷启动已执行：建了 `projects/cogos/entries/code-map.md`（纯搬运旧 code-structure + bugfix 不变量，缺失标「待补」，已提交）。反思后确认方向有误，地图应重建。

## 旧方法的毛病

旧图是「从文件名 + 旧文档猜」搭出来的，两个直接证据：
- `entry.py` 被猜成「入口（待补）」，实为消息结构，与 ws/session 相关——不理解项目就归不对组。
- 「通信线」是自造标签，项目自己无此概念，连作者都说不清指什么。

## 新思路（本次讨论达成）

1. **目的优先，代码是已实现子集**：地图建立在对项目目的 + 设计的完整理解上；设计文档里有未实现/被放弃的部分，纯代码图会丢失；调试前提是知道「代码为什么存在、想干什么」。
2. **新增「状态」轴**：每模块标 已实现/未实现/折中/不合理；「不合理/折中」记为「疑问/待核」而非断言，保持可复核。
3. **完整理解 ≠ 完整复制**：图是理解的骨架 + 分层 + 指针，细节留本体文档；树型 + 按需加载解决规模（人脑大图类比：脑子里是树，细节在文档，知道去哪找）。
4. **维护是循环问题，不是大小问题**：AI 触发更新 + 人纠偏；原 code-structure.md 废掉是因为没有维护循环（一次性产物），不是因为它大。
5. **验收分工**：AI 逐条验形式（可交 subagent 打破自审偏差，只报形式层面达标/红线，不报「通过」）+ 人通读验实质（拿代码记忆对照易错点）。
