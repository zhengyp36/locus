# worklog — cogos

YZ 自行维护的工程记忆。

为什么 AI 与 YZ 分别维护记忆？
1. YZ 在阅读 AI 的工程记忆时感觉到不好理解，或许思维方式有差异。
2. 收口时各自独立写总结，可以看到二者的差异，有利于对齐重点和结论。

- `README.md`（本文件）— 协作方法论：kilo 与 YZ 怎么一起推进。
- `STATUS.md` — 重要结论索引（指向 `../entries/` / 本体 doc）+ 当前现状 + 下一步计划；收口时重写。
- `LOG.md` — 每天日志，最新在最前；长了归档为 `LOG-YYYYMMDD-YYYYMMDD.md`（标出时间范围）。

## 协作方法论（2026-10-19 定）

kilo 与 YZ 一起推进设计与落码。

1. **决策三层，共同讨论对齐并形成结论**
   - 方向（做什么 / 目标 / 边界）。
   - 选型（走哪条路）。
   - 实现细节（代码怎么写 / 结构长什么样）→ 动手暴露、不前置纠结。
2. **结论锚到代码**：每个收口结论要么落到 commit / tag / 测试，要么显式标「纯讨论、未落码」；不锚代码的结论只是素材，会漂。
3. **YZ 按结构层过问代码**：kilo 落码后交「结构说明 + 关键文件 + 验收结果」，YZ 核数据流 / 模块边界 / 接口 shape，不只看结论文字、也不逐行读。
4. **结论三态**：活跃（用）/ 参考（可看但不当作定论）/ 废弃（明确不用）；清点快速裁决，判不了的标「悬置」带进讨论，不当场展开。

节奏：讨论思路 → 定结论 → 落码 → YZ 看结构 / 验收 → 蒸馏进记忆。

## 为什么这么定

之前的问题有两个，其实是一个：**结论和代码脱了钩**。

- 过于纠结、一直没动手：决策和动手被拆成两段，讨论失去收敛的抓手，任何岔路都能再想一层，决策悬空等一个永远不会来的"想清楚"。
- 几乎不过问代码：结论没锚到代码，记忆只剩叙述，会漂、堆积、互相矛盾；而不看代码又反过来让讨论失去真实约束，加剧纠结。

解法不是少决策，也不是逐行读码，而是**决策分层 + 结论锚代码 + 结构层 review**。

## 被否的方案

- 「YZ 自推、kilo 退回编程手」（2026-10-15）：没治到代码脱钩这个根，反而更少过问代码、更浮于表面。
- 「YZ 逐行读码」：代价大、没必要，结构层 review 已够。
- 「让 YZ 少做决策」：根因不是决策权在 YZ，是决策与动手分离。
