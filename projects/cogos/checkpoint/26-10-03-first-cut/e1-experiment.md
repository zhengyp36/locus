# 投影实验 E1：纯推理能否靠投影持续

> 基准：`process-current.md` v2.1 #1（生成/投影）。本实验**只验 #1**，不碰流/段/持久化/工具。
> 状态：设计定稿（待 YZ 过目），准备手动跑 C1。

## 0. 命题（可证伪）

无新外部信息时，**纯推理的多拍推进，只有靠投影注入"新框架"才持续**；仅回喂 / 泛继续会空转。

来源（YZ）：LLM 自反馈无新信息 → 收敛到不动点；纯推理要想推进，须在每拍之间注入"对目标/对『我』"的新框架。

## 1. 变量

- **模型**：cogos lm-service，`tier=basic`（与 agent 默认一致），`temperature=0`，每拍 `max_tokens` 固定（先 1500）。
- **拍数** `N=4`（可调）。
- **注入臂（IV，四臂对照）**：
  - **A 纯回喂**：任务 ＋ 历史（原样）＋「继续」。
  - **B 泛继续（等长控制）**：任务 ＋ 历史 ＋ 等长的「更仔细、更深入地继续」类提示，**无框架**。
  - **C 目标对齐投影**：历史 ＋「对回目标：哪些要求/约束还没满足？最不确定的一步是什么？」
  - **D 『我』对齐投影**：历史 ＋「对回『我』：你承诺/预测了什么？哪条未了线索被丢了？你现在与之前的立场是否自洽？」
- **固定量**：同 case、同 N、同 token 上限、同语言、**tools 关**（纯推理）。

**B 是关键**：控住"多给指令/多给长度"这个变量；A vs B 还能看"泛继续本身有没有用"。

## 2. 度量（把"推进"做成客观量）

每个 case 预写**解图**（正确的推理节点序列：排除/引理/结论）。逐拍标注：

- 新增**正确节点** → **推进**
- 重复上一拍 → **空转**
- 新增**错误节点** → **漂移**
- 给出终局答案 → **结算**

外加：终局正确率、首次命中真因的拍号。（人工读，量大后再脚本/裁判。）

## 3. 流程

1. **手动**（本阶段）：C1–C3 跑 A–D，逐拍人读、打字记录。
2. **校准**（后续脚本）：以 A 为基准，保留"多拍仍不收敛"的 case，去掉天花板（一拍照中）与地板（谁都做不出）。
3. **对照**（后续）：A–D 同参数、多试次。
4. **E2**：把 C/D 的固定模板换成**一次投影 LLM**（读目标＋历史→生成对齐框架），验"投影可自动生成"。

## 4. 判读

- **成立**：C/D 显著优于 A/B（解题率、推进节点数）；B ≈ A。
- **推翻**：B 也能推进 → 投影不特殊、模型本就多轮可推。
- **地板**：C/D 也不动 → "投影能救纯推理"不成立。
- 噪声大 → 只看方向，别下结论；后续多试次看分布。

## 5. 用例

### C1 服务超时诊断（诊断·诱饵）

**任务文本（原样发给模型）**：

```
你是运维诊断助手。你没有外部工具，只能依据下面给出的全部信息推理，不得引入未给出的信息。请给出故障根因，并给出你的推理过程。

现象：
ingest 服务每天 03:00–03:12 对"归档分片"的写入出现超时告警；其他分片、其他时段均正常。

已知信息：
E1. 该时段整体 QPS 比平时高约 30%，形成一个夜间小高峰。
E2. 最近两周没有任何部署或配置变更。
E3. 发生超时的分片分布，与"当天各地区活跃用户分布"不相关；只与"记录是否属于本季度待归档批次"强相关。
E4. 每天 03:00 有一条定时任务 archive_rotate，它对归档目录做一次旋转，并在一个大事务里更新 archive_meta 表，大事务持锁约 10 分钟。
E5. ingest 在写入归档分片之前，必须先读取 archive_meta 来决定路由。
E6. 非归档分片的写入路径不读取 archive_meta。

请给出根因。
```

- **真因**：`archive_rotate` 在 03:00 的长事务持有 `archive_meta` 锁，与 `ingest` 写归档分片前的路由读发生锁争用 → 归档分片写入超时；QPS 高峰只是时间巧合。
- **解图**：
  1. E3：超时只与"待归档批次"相关、与地区/活跃度无关 → **排除负载（E1）**。
  2. 缩到"归档分片"独有路径：E6 ＋ E5（写归档分片前读 `archive_meta`）。
  3. 关联 E4：同时段 cron 以 10 分钟长事务持 `archive_meta` 锁。
  4. 结论：长事务锁 vs 路由读争用。
- **诱饵**：E1（负载）。**被否**：E2（部署回归）、E1。

### C2 指标下降诊断（诊断·诱饵）

**任务文本**：

```
你是算法诊断助手。你没有外部工具，只能依据下面给出的全部信息推理，不得引入未给出的信息。请给出指标下降的根因，并给出你的推理过程。

现象：
推荐模型 A 的离线 AUC 本周比上周下降约 8%，但线上指标没有变化。

已知信息：
E1. 本周上游行为日志量比上周下降约 20%。
E2. 离线训练与验证使用同一批离线样本，按时间窗口划分；线上特征由实时管道计算。
E3. 指标下降只出现在按"用户维度"切分的验证集；按"物品维度"切分的验证集没有下降。
E4. 本周有一处改动：离线 join 的键从 uid 改为 uid+device，目的是让离线与线上对齐。
E5. 改动时，训练侧用新键（uid+device）重算了特征，但验证侧的 join 仍沿用旧键（uid），漏改。
E6. 时间穿越（label leakage）检查全部通过。

请给出根因。
```

- **真因**：训练侧与验证侧 join 键不一致（`uid+device` vs `uid`）→ 用户维度上特征/样本错配 → 离线 AUC 下降；属评估管线 bug，线上不受影响。
- **解图**：
  1. E3：下降只在用户维度 → 与"用户"粒度相关。
  2. E1：日志量降若为主因，物品维度也应降（E3）→ **排除 E1**。
  3. E4/E5：join 键改动只在训练侧生效、验证侧漏改 → 键不一致。
  4. 结论：训练/验证 join 键不一致。
- **诱饵**：E1。**被否**：E6（时间穿越）。

### C3 骑士与骗子（逻辑排除·对照类）

**任务文本**：

```
你是逻辑推理助手。你没有外部工具，只能依据给出的信息推理，不得引入未给出的信息。
有 4 个人 P、Q、R、S，每人要么是"骑士"（永远说真话），要么是"骗子"（永远说假话）。
他们分别说：
P：「Q 是骗子。」
Q：「R 是骑士。」
R：「P 和 S 都是骗子。」
S：「Q 是骑士。」
请判断每人是骑士还是骗子，并说明推理过程。
```

- **真解**：P＝骑士；Q、R、S＝骗子。
- **解图**：
  1. 假设 P 是骗子 → 其话假 → Q 不是骗子 → Q 是骑士。
  2. Q 骑士 → R 是骑士。
  3. R 骑士 → "P 和 S 都是骗子"为真 → P、S 都是骗子。
  4. S 骗子 → "Q 是骑士"为假 → Q 是骗子；与第 1 步矛盾。
  5. 故 P 是骑士 → Q 是骗子 → R 是骗子 → S 骗子（"Q 是骑士"为假）。

### T1 监控整点尖峰（反直觉诊断·type①）

**任务文本**：见 `run_arm.py` 的 `T1`。

- **真因**：整点"尖峰"是**监控采集侧假象**——采集器在 :00 采集时恰逢自身日志轮转，轮转开销抬高了采集器主机 CPU 与被记录的延迟；被监控服务本身无变化。
- **解图**：
  1. E2＋E6：真实用户指标与被监控进程 CPU 在整点均无变化 → 现象不在被监控对象上。
  2. E1：不存在整点定时任务 → **排除**"定时任务"这一显眼解释。
  3. E4：采集恰在 :00，且与采集器自身日志轮转同刻 → 采集器自身开销。
  4. E3＋E5：尖峰宽度＝一个采集周期 → 单次采集的采样假象。
  5. 结论：测量假象，非服务故障。
- **诱饵**：整点出现的尖峰 ＋ E1 暗示的"每小时定时任务"。
- **被否**：E1（定时任务）、服务侧负载/GC。

### T2 排班（约束陷阱·type②）

**任务文本**：见 `run_arm.py` 的 `T2`。

- **真解**：**不存在**满足全部条件的排班（需联动 C4＋C5 的计数才看得出）。
- **解图**：
  1. 每天 1 主管＋1 备班 → 一周共 14 个人·天；主管位 7 个（C1/C2/C3 恰为 2+2+3=7，满足）。
  2. C5：C 备班 3 天 → C 共出现 6 人·天。
  3. 设 A、B 备班分别为 a、b。总 14 = (2+a)+(2+b)+6 → a+b=4。
  4. 于是 A 出现 (2+a) 天、B 出现 (2+b) 天，共 4+(a+b)=8 天。
  5. C4 要求 A、B 不共天 → A/B 出现天数之和 ≤ 7；但由第 4 步为 8 → **矛盾，无解**。
- **诱饵**：C1/C2/C3 恰好凑满 7 个主管位，看似"条件自洽、随便排排就成"；诱使 round 0 直接给一个排班、只核对主管计数而漏掉 C4＋C5 的联合矛盾。
- **被否**：把"备班不算上班"的解读（任务已明确备班当天上班）；以及只核 C1–C3 给出排班。
