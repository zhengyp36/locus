## 十三、为什么“CPU 尖峰”和“延迟尖峰”会同时出现且同步

这一点容易被误认为“服务真的同时 CPU 高、延迟高”。但在采集伪影场景下，同步出现反而更合理：

1. **同一采集器、同一采集周期**
   - CPU 和接口延迟很可能由同一采集器在同一时刻抓取或聚合。
   - 采集器自身在整点轮转时 CPU 紧张，会同时影响多个指标的采集质量。

2. **采集延迟会污染延迟指标**
   - 若采集动作被延迟，接口延迟的测量窗口可能被拉长或错位。
   - 结果就是延迟指标出现异常高值。

3. **采集器 CPU 可能被误算入服务 CPU**
   - 若监控系统按主机维度聚合 CPU，采集器所在主机的 CPU 抖动可能被算进图表。
   - 即使按进程维度，采集器自身异常也可能导致采样值错误。

4. **折线图同步放大**
   - 整点 :00 一个异常采样点，在 CPU 和延迟两个图上同时出现。
   - 折线连接后，两个图都表现为约 15 秒宽的同步尖峰。

所以“CPU 和延迟同时尖峰”并不证明服务真实故障，反而与“同一采集器在整点被自身轮转干扰”高度一致。

## 十四、为什么用户侧指标完全无变化是关键证据

用户侧指标系统与监控系统不同源，这意味着：

- 它不依赖同一个采集器；
- 它不受采集器主机日志轮转影响；
- 它直接反映真实用户请求的成功率和延迟。

如果服务真的每个整点 CPU 升高、接口延迟升高，用户侧至少应出现：
- 延迟上升；
- 成功率下降；
- 超时或重试增加。

但 E2 显示用户侧完全无变化。这说明：

- 服务真实处理路径没有异常；
- 监控图上的尖峰没有传导到真实用户；
- 尖峰只存在于监控数据世界。

因此 E2 是区分“真实故障”与“观测伪影”的决定性证据。

## 十五、为什么服务自身 CPU 另一来源平稳也是关键证据

E6 说明：

- 被监控服务自身进程 CPU 由另一采集来源监控；
- 尖峰期间保持平稳。

这直接否定了“服务进程在整点 CPU 升高”的解释。结合 E2，可以得出：

- 服务进程 CPU 平稳；
- 用户侧体验平稳；
- 只有监控系统图上的 CPU 和延迟出现尖峰。

这三者同时成立，只能说明问题出在监控系统，而不是服务本身。

## 十六、如何写故障报告

可以按以下结构写：

### 标题
监控整点 CPU/延迟尖峰根因分析：采集器日志轮转导致的观测伪影

### 现象
监控仪表盘每个整点出现约 10 秒 CPU 与接口延迟尖峰，其他时间平稳。

### 根因
监控采集器在整点 :00 采集时刻同时进行大日志文件轮转，轮转短暂占用采集器主机 CPU，导致整点采样点异常；折线图将单点异常连成约 15 秒宽尖峰。

### 证据
- E1：服务侧无整点定时任务。
- E2：用户侧指标整点无变化。
- E3：监控每 15 秒采样，折线连接。
- E4：整点采集与采集器日志轮转同刻。
- E5：尖峰宽度约等于采集周期。
- E6：服务自身进程 CPU 整点平稳。

### 结论
不是服务真实故障，也不是服务侧定时任务，而是监控采集链路伪影。

### 修复
- 错开日志轮转与采集时刻；
- 降低轮转对采集器 CPU/I/O 的影响；
- 采集器与轮转解耦；
- 监控采集器自身健康度；
- 图表与告警避免单点异常误报。

## 十七、最终一句话

**整点尖峰是监控采集器在整点轮转大日志文件时，把自己的 CPU 抖动写进了监控图；被监控服务本身整点完全正常。**
