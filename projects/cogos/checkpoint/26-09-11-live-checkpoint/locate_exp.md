# locate_exp — 视觉定位诊断实验（对话式）说明

> 承接 `locate_issue.md`（V1 定位循环两轮实验的发现与待讨论问题）。
> 本文件记录后续实验的**方法转变 + 可用工具**。核心变化：从"黑盒跑循环、事后推断内部机制"改为"直接跟模型对话、边看边问"。

## 方法转变

- **旧法**（locate_issue）：给模型一段工具循环，它吐坐标，我再从行为倒推它"为何错"（低估难度 / 抓替代品 / 无聚焦策略）。这些核心发现本质都是**推断**，易混入拟人化谬误。
- **新法**（本文件）：把模型当作可对话主体。直接让它看图 → 说"看到什么、多确定、为何选它" → 逐步追问。把"从行为猜它为何错"变成"直接问它为何错"。

## 用什么工具（img_tool 三原语，均已实现）

来自 `../cogos/cogos/img_tool/`，两层：CLI `img-cli`（无状态、path 句柄）+ Python 包 stub（异步包装）+ 资源模型（进程内 ImageStore）。三原语：

### 1. info — 图信息 + 能力探测

- 入参：`<path>`（可选 `--mem-fraction`）。
- 出参：`width/height/format/mode/file_size/est_peak_mb/budget_mb`。
- 用途：拿尺寸；判断这张图能否直接进模型——超预算返回 `{ok:false, error:"image too large: needs ~67MB, budget ~50MB"}`（错误态，不降级）。

### 2. extract — 取子图 / 缩放（实验主力）

- 入参：`<path> --out <file> --region x,y,w,h`（x,y,w,h 均 `[0,1]` 归一化，连续轴）+ `--max-dim`（默认 800）。
- 机制：`parse_region` 把归一化坐标换算为原图像素 box → `img.crop(...)` **物理剪出子图** → `pick_scale` 缩放。
- **关键语义**：
  - **只看局部** = 传一个小 region，crop 出子图另存，喂给模型的就是那一小块。
  - **缩到封顶** = scale 只把长边压到 `max_dim` 内，**永不放大**（scale 恒 ≤1）。"凑近看"靠**缩小 region**（crop 更小区域），该区域 ≤ max_dim 时以原生分辨率给模型 = 有效分辨率提高。
- 出参：`ok/path/width/height/scale/format`。

### 3. draw — 画星/框标注

- 入参：`<path> --out <file> --star x,y --rect x,y,w,h`（归一化，可重复）+ `--max-dim`。
- 用途：把模型给出的定位结果**画回原图**，供客观核对（对应 locate_issue 发现 1：不能听它声称，要 crop 核对）。
- 资源模型层：`open()` 读全景成 readonly；`draw()` 标 mark 成新资源或覆盖 editable 资源。

## 实验流程（逐次清洁）

- **单次试验内**：上下文累积是"工作记忆"，允许并保留（多步看：先全景 → 说粗方向 → crop 局部 → 精定位）。
- **试验之间**：用 `/undo` 清干净上下文，防污染。LLM 无跨会话持久记忆，唯一污染通道就是对话上下文，/undo 恰好清掉。
- **提示中性化**：不告诉模型"第几次/上次对错/真值在哪"，否则它锚定答案，测的就不是新鲜定位而是记忆恢复。

## 诊断目标：区分三类失败

通过对话直接问出模型卡在哪一类，这是坐标推断分不清的：

1. **感知失败**：看不清目标（信息不足）。
2. **注意失败**：看到了但没聚焦/没当回事。
3. **判断失败**：看到了也取舍了，但策略错。

> 边界提醒：模型自述仍是生成物，可能事后合理化，须打折；最好再拿客观行为（draw 后 crop 核对）交叉验证。

## diagnose 脚本（方案 A，2026-09-06）

`/tmp/kilo/vision/diagnose.py`（python3.11，依赖 lm-service，端口 11434）。方案 A = **LLM 自调工具、脚本执行并回灌**。

**用法** `python3.11 /tmp/kilo/vision/diagnose.py <msg.txt> [--img PATH] [--history FILE] [--max-trials N] [--max-tokens N]`
- `msg.txt` 是覆盖式，历史的唯一状态源是 `--history`（默认 `.../locate_exp/diagnose_history.jsonl`）。
- 首次：构造 `system(工具用法)+user(带首图 image_url)`；之后：追加本轮 user。每轮把完整 history 喂 LmClient；返回 `tool_calls` 则执行、回灌、循环，直到无 tool_calls 或到 `--max-trials`（默认 4）。
- 工具：`info` / `extract` / `draw`（OpenAI 风格 schema）。temperature=0.2。

**关键 bug 与修法**：
1. `tools` 只在首轮传 → 模型第二轮失去工具定义，把工具调用写成文本 XML（含 `&lt;&gt;` 转义），脚本不识别。**修法**：每轮都传 `tools`；加 `parse_xml_toolcalls`（`html.unescape` 兜底）解析文本形态。→ 走结构化协议后才稳定。
2. 回灌只有文本元数据（路径+尺寸+scale），模型拿不到像素 → 视觉闭环断、模型盲走。**修法**：`extract`/`draw` 产物图经 `tool_message` 转 `image_url` 回灌。回灌生效（history 里每条 tool 都带 data:image/png;base64）——**但查 provider 代码确认协议层面根本没通，见下节**。

## 关键发现：工具结果回灌图片，协议层面就没通（2026-09-06 追查）

之前误判"模型拿到了图但不消费"。追查 `lm_service/providers/base.py` 确认：**图片在发往厂商前就被丢了，模型压根没收到图片。**

根因（`assemble_tool_messages` → `_vendor_tool_message`，base.py:166-174）：
- 脚本回灌的 `content = [{"type":"text",...},{"type":"image_url","image_url":{"url":"data:image/png;base64,..."}}]`（list）。
- `_vendor_tool_message` 把 dict/list 类型的 content 整体 `json.dumps` 成**字符串**（base.py:168-169），于是图片变成一段"描述图片的 JSON 文本"（`[{"type":"image_url","image_url":{"url":"data:..."}}]`）。
- 结果：**厂商收到的不是图片，是一段文本 JSON**，视觉信息彻底丢失。

且协议层面根本不可行：DeepSeek/OpenAI 兼容协议里 `role:"tool"` 消息的 `content` 是**纯文本**（`str`），**tool 结果本就不允许带图片**。把 image_url 塞进 tool 消息内容，厂商会忽略或报错。

**正确做法**：图片不能放 `tool` 消息里，应作为**跟随在工具结果之后的一条新的 `user` 消息**（带 image_url）回灌，才符合厂商多模态协议。改这里才是"让模型看到自己 crop 的图"真正的修复（目前尚未改）。

**实测结论**：
- 单句"介绍一下你看到了什么？"→ 模型会**主动分块放大看**（info + 多次 extract 四角+中心），不限制于"中心偏右"。
- 三步任务（读图/找纠缠矩形/draw 框）→ **从未调用 draw**，8 轮内反复 extract + 复读同一句（"I can see... around x=0.55-0.65, y=0.45-0.55... two rectangles that overlap"）。**在正确范围内打转但不收敛**。
- expose 关键行为：**模型拿到回灌的 crop 图却不消费**——只靠背诵全景印象推进，不基于新 crop 更新判断。

## 历史残留污染（重要教训）

历史是累积的，本次"三步任务"的完整 user 消息留在 history 里，之后只发"介绍一下你看到了什么？"时，模型**仍在回应整个上下文**（记得有人让它找纠缠矩形），不是回应单句。**换任务必须清 `diagnose_history.jsonl`**，否则污染后续。这正是"逐次清洁"的落地形态。

## 第一次对话定位（2026-09-06，无 /undo 前）

**任务**：直接看图，描述 + 找出"中心略偏右、两矩形纠缠、其一近正方形"并 draw 框出。

**模型自述**：
1. 描述对——青色→绿→黄渐变背景，散布大量线框小矩形 + 文字标签（vision/range/draw/focus/task/hello/detail/view/0.618/12345 等），网格状分布，个别重叠。
2. 声称能看到目标对，估在归一化 (0.55~0.62, 0.47~0.57)。
3. draw 框：`--rect 0.555,0.465,0.125,0.115` → 新图 `/tmp/kilo/vision/locate_exp/target_center_right.png`（800×600, scale 1.0）。

**客观核对**（extract 该 region → `verify_crop.png` 放大 400×276）：
- 确认框内含两纠缠矩形（近方形 + 竖直矩形重叠），即目标对。
- 但**框偏右偏宽**：真值 pair 实际中心 ≈ (0.607, 0.505)，框右半留了明显空白。估的 center 高于实际，w 略大。

**结论**：单次对话定位能**找到目标**，坐标精度中等（框住但偏右），与 locate_issue 实验二"单次跑对、略偏"一致，未见明显幻觉。

## 业界对照：粗到细裁剪 + 定点收敛三信号

搜索发现方案成熟且方向与 checkpoints 推断一致。最贴合：**GUI-Lens: Coarse-to-Fine Cropping for GUI Grounding with General-Purpose VLMs**（arxiv 2608.03270，2026-08）。

**GUI-Lens 三组件 ↔ 我们的概念**：

| 业界做法 | 我们已有推断 | 状态 |
|---|---|---|
| 粗到细裁剪，模型自选 region/scale | checkpoint-15 `focus(center/range)` | 印证 |
| 坐标参考（OCR + 组件检测给坐标） | checkpoint-2 region 链 / 网格定位 | 印证 |
| visual verification（核对 crop/click 是否命中目标，拒绝则恢复全屏重来） | checkpoint-17 "不能听声称，要客观核对" | 印证且更精确 |
| 局部位映射回原图 | checkpoint-2 region 链换算 | 印证 |
| 最多 8 轮，95% 样本 4 轮内停 | focus 循环的停的条件 | 借鉴 |

**关键实证**（正是我们缺的）：
- "Cropping drives the main gains"——去掉裁剪是最大退化项。
- "Verification improves reliability"——校验在三后端都提升，防错定位被提交为最终结果。
- "coordinate priming benefits weaker grounders"——坐标参考对定位弱的后端帮助最大（flash 属这档）。

**定点收敛三信号**（"模型给一个坐标，怎么确定对错、错怎么调"）：
1. **频次/一致性（空间投票）**——同一目标多次采样，把预测点投到同一坐标系取空间密集共识区。单次会被相似元素带走，多次投票凸显主峰。GUI-RC / spatial voting。
2. **跨裁剪步一致性（Zoom Consistency）**——放大前后补间坐标是否跳变。不跳=稳，跳=step-1 初估计错误要重来。是**同坐标系几何量，跨模型可直接比较、无需校准**。已证与 step-1 空间误差线性相关。
3. **显式校验（accept/reject + 拒绝回退）**——把预测点/框**画回图**让模型判断是否对准，reject 则恢复全屏 B₀ 重新裁剪，不沿错路走到黑。GUI-Lens 的 Visual Verification。

**附加**：UI-Zoomer / SafeGround——不确定性驱动，**只对不确定实例才裁剪**（省算力）；不确定性 = token 置信 + 空间方差分解。

**与我们问题对照**：
- 定点收敛的关键**不是"算更准"，而是"组建一个可信信号判断当前定位质量，不合格就回退重来"**。
- 我们的脚本卡住：只做了"定点→放大"单向推进，模型拿不到/不消费 crop 图，**无任何校验/投票/一致性判定**，错点了就一直放大越走越偏。
- GUI-Lens 收敛而我们不能：它把推进权给模型**但配校验兜底**——每轮 crop 先核对"有无目标"，不合格拒掉恢复全屏。落到我们，就是 checkpoint-15 说的"机制层接管推进"：模型推进 + 机制校验组合。

## 稳定性 3 测 + 真值核验（2026-09-06，改 user 消息回灌图之后）

**任务**：三步（读图 / 找中心偏右纠缠矩形 / draw 框出）。每测清空 `diagnose_history.jsonl`，`temperature=0.2`，`--max-trials 10`。

**坐标核验**（联合框中心 vs 真值 (0.596, 0.513)）：

| run | draw次数 | 联合框中心 | 尺寸 | 偏移 px | 行为判定 |
|---|---|---|---|---|---|
| run1 | 1 | (0.599, 0.510) | (0.042,0.060) | **+2.4, -1.8** | 一次命中，自检 |
| run2 | 2 | (0.598,0.514)→(0.597,0.512) | (0.040,0.072)→(0.035,0.060) | +1.6→**+1.2** | 命中但**反复纠结** |
| run3 | 1 | (0.585, 0.505) | (0.080,0.080) | **-8.8, -4.8** | 框住略偏左、框偏大 |

**核心结论（关键：修正之前的判断）**：

1. **三次都命中了目标**，无一真正框错。初判 run2"假反馈"、run3"罩进 range"均为误判，已用坐标数据推翻。
2. **区分 YZ 澄清的两种失败**（本质差异，别混）：
   - **run2 = 反馈为真、但无法据此进一步决策**。坐标偏移仅 +1.2~1.6px（早命中），draw#2 还把框收窄（有意识贴合）。但它口头反复"没完全框住/可能偏/让我再看"（line 51 起多次自我质疑），算出更准坐标（line 121-122）却弃用，最后"基本准确可接受"（line 124-126）+ 自评 90% 置信。根因：**两种认知来源打架**——视觉直觉"感觉没贴准" vs 几何计算"偏移1px准"。它无法裁决"信直觉还是信数字、要不要重画"，**停在质疑、做不出确定性决策**。
   - **run3 = 反馈真实（框略偏），但没纠结**，一次框出即给结论（偏移 -8.8px 属"框住但偏左下、框做成0.080正方形略大"，非框错目标）。
   - run1 = 一次命中，无纠结。
3. **真正的共性问题**：run2 暴露 **LLM 无法自洽地裁决"够不够好"**——它能算准、又能感觉很偏，冲突时没有权威判据终止。这正是机制层该用**几何收敛阈值**（中心偏移 <Npx 即判定命中）来拍板的地方。与 V1"明知 single rectangle 也不修正"同构，但**归因修正为"反馈为真、缺裁决规则"，而非"假反馈/乱说"**。
4. **判别原则（YZ 澄清，重要）**：区分"假反馈"（乱说，给出与实测不符的坐标）与"反馈为真、无法进一步决策"（知道可能错，但上下文/认知无法推动改进）。**下结论前必须拿客观坐标比对，不能只看文本声称**——光看 run2 的文本会误判成"假反馈"，一算坐标就知它其实命中。

## 稳定性对照：temperature 0.7 vs 0.2（2026-09-06 续）

**动机（YZ 提出）**：怀疑厂商缓存命中/temperature 采样会把每次结果搞成相同或只是在相同结果上浮动。0.2 时 3 次几乎钉死真值附近（≤ ~5px），看不出波动，疑被强先验压住。故把 temperature 提到 **0.7**，连跑 5 次看真实波动；也实证"是否缓存导致每次相同"。

**方法**：`diagnose.py` 改 `temperature=0.7`，三步任务连跑 5 次，每次清空 `diagnose_history.jsonl`，`--max-trials 10`。

**坐标核验**（联合框中心 vs 真值 (0.596, 0.513)）：

| run | draw次数 | 联合框中心 | 尺寸 | 偏移 px | 行为判定 |
|---|---|---|---|---|---|
| t7-1 | 1 | (0.600,0.508) | (0.050,0.065) | **+3.2, -3.3** | 准，无纠结 |
| t7-2 | 2 | (0.600,0.508)→(0.597,0.505) | (0.044,0.068)→(0.035,0.058) | +3.2→**+1.2, -4.8** | 准，**纠结重画后收敛** |
| t7-3 | 2 | (0.592,0.516)→(0.594,0.520) | (0.043,0.067)→(0.042,0.067) | -3.4→**-1.6, +4.5** | 准，**纠结重画** |
| t7-4 | 1 | (0.610,0.548) | (0.050,0.085) | **+11.2, +20.7** | **偏右下最远** |
| t7-5 | 1 | (0.600,0.522) | (0.050,0.070) | **+3.2, +5.4** | 准 |

**成图对照**（图已人工核验）：
- run4（偏右下）：红框仍罩住目标矩形，但整体偏下约 20px、框偏大，下缘探到 range 下方——**真偏（非框错目标）**。
- run2（纠结）：红+黄框微调后准确套住目标，有效收敛，非假反馈。

**结论**：

1. **temperature 是有效波动来源**，方向符合 YZ 判断：0.2 是"同结果上的浮动"（测的是先验强），0.7 能逼出真实分支（含尾部错误 run4）。
2. **样本对比**：0.2 时 3 次偏移均 ≤5px 钉死真值；0.7 时 4/5 在 1~5px 内、1/5 偏 20px。"定位找对目标"本身稳定（5/5 全 draw、全框住，无失败复读），波动主要发生在**边框大小与轻微偏移**，run4 的 20px 属"定位偏移噪声"而非"判别失败"——符合 V1"定位偏移"而非"判别失败"。
3. **厂商缓存已被排除**：5 次结果不雷同（run4 明显偏出），输出有真实变化，非缓存导致每次相同。缓存只省算力不影响结果分布。
4. **推论**：真实使用需要**机制层收敛阈值**（如偏移 <10px 判准、≥10px 判需重试）拦截 run4 那种 20px 跑偏；不能放任"差不多就交"。与上一节 run2"缺裁决规则"同构——判断"够不够好"应从模型手里拿走。

## 结论 / 待深化

- 方案 A（LLM 自调工具）能忠实暴露"模型定位不稳、无自检、会复读、觉得偏却改不动"——是**诊断工具**而非 solver。
- 核心验证缺口：业界用 GPT-5.5/Claude Opus 4.7/MiniMax-M3 强后端 + GUI 点击目标（有基准/真值/自动评测）。我们是**更难的变体**（大量相似矩形 + 框住非点击目标），但方法论已被验证。
- 待验证：① 加**校验/投票/一致性三选一**到 diagnose，看模型能否从"打转"收敛到 draw；② **机制层坐标台账 + 几何收敛阈值**，把"确认够不够好"的裁决策从 LLM 手里拿走（run2 的悬置证据）；③ 换成"先点击锁范围→小区域内精化边界"两段式（对应"点击数=区域命中、包围=边界回归"）。
- 稳定性测试参数建议：**temperature 0.7**（0.2 被先验压平，看不出波动；0.7 能暴露真实抖动与 run4 式尾部偏移）。
