## 本会话已定论（别重炒）

1. **机制与流程解耦**：不做 driver loop，只挂**轮次边界**；不规定 agent 是循环还是事件驱动。
2. **轮次 = 一次模型动作**（工具调用，或结束动作）；**完成也算动作**。
3. **打断 = 执行前丢弃本轮动作 + 注入**；强制靠**闸门**（未对账不许执行），丢弃只决定打断时机。
4. **提醒分软 / 硬**：软 = 计划中点纯提醒、可不回应、**不升级**；硬 = 丢弃 + 必须工具动作回应。
5. **不把软升级为硬**：硬锚在**计划时钟**（`budget_rounds`）上，无视软绕不过硬。
6. **计划变更**：`adjust_plan`（只动当前及后续）/ `rebuild_plan`（要改前面只能重写）；预算**累积**（已用不补回）。
7. **不做语义复杂度判断**：`Σ ≤ total` 直接接受，超了才协商（"复杂"是结果）。
8. **`reason` 仅 check-in 时必填**（程序处理不了自由文本，理由进参数）。
9. **上下文压缩会驱逐计划**：靠 `[check-in]` 重注入兜底。

## 讨论队列（审核问题清单）

### A. 必须先解的自洽问题（逻辑 bug / 矛盾）

1. **硬触发是"电平式" → check-in 死循环**（§5.1/§5.2）。`actual_rounds ≥ budget_rounds` 一旦成立就永远成立；模型以 `update_progress`（≈`continue`）对账、未改预算 → 下一动作又被丢弃 → 无限 check-in（最后被 `drop_streak` 误杀）。需**消抖 / re-arm**（对账后推进触发点，或规定 `continue` 必隐含"该步预算上调 / 该步结束"）。
2. **预算算术不自洽**（§4.2/§7）。`spent + Σ ≤ total` 若 `Σ` 含**已发生行**会重复计算 → 应写死 `Σ` = **未完成行**预算和。且 `spent`（所有动作）与 `budget_rounds`（工作轮次）**口径不同**——计划/对账/被丢弃动作算不算 budget？必须定。
3. **`spent` 与 `actual_rounds` 关系未定义**（§2.1/§5.2）。谁在何时 +1？"当前步"怎么判定（不设 `in_progress` / 设多个）？没有这条，per-step 与 total 对不上账。
4. **协商回应通道缺失，且与"只认工具动作"矛盾**（§4.2）。"模型说不能"没有工具表达 → 规定：能 = 重调 `build_plan`/`adjust_plan` 压低 Σ；不能 = `finish_task(aborted, reason)`。
5. **"裸停"（不发 `finish_task`）未处理**（§5.2）。模型可直接输出文本停下、绕过终态。需规定：非 `finish_task` 的结束动作 → 视为提前结束 → 强制补总结 / 记 `aborted`。
6. **完成仍是自报**（§5.1/§5.3）。`done_marker` 是**计划时判据文字**、不是**证据**；且只在 check-in 校验非空。空 ✓ 未堵 → 至少提为**每次写表的 schema 校验**，并区分**判据 vs 证据**（证据存哪？现无字段）。

### B. 需补的块

7. **`paused` 状态缺失**（§4.2/§9 用"暂停"，§2.2 `phase` 无此值）。
8. **P1 拦截循环没写**（§3/§9）：计划前收到非 `build_plan` 动作怎么处理？R 怎么数？纯文本怎么办？
9. **`finish_task` / `todo_read` 的返回未定义**（§6.4）。
10. **`past_row_modified` 只对 `adjust_plan` 成立**；`rebuild_plan` 本就要改前面（§6.4/§9 需注明）。
11. **软触发"可重复"含糊**（§5.1）：半预算只响一次，还是每 K 响？与"默认 = 半预算"冲突。
12. **停滞定义偏弱**（§5.1）：若 #1 未解，硬对账难接连发生，"连续 2 次无变化"难触发。

### C. 缺的整块内容
