# Checkpoint 12 — 认知图必要性质疑 + 方向修正

> 日期：2026-09-01。状态：讨论中，未写代码。接口设计推进途中，YZ 提出根本性质疑：认知图是否「根据理论设计」而非「根据实际需要」，方向待重新定位。

## 一、质疑：认知图必要性是假定的，不是逼出来的

### 1. cu vs 认知图的「直接感受」差异

- cu：有「就应该是这样」的直接感受——必要性是物理的（LLM 一次 forward 原子，跑完整任务必须壳来多次调用 + 管状态 + 收敛），从「LLM 是什么」直接推出，无中间假设。
- 认知图：没有这种感受——必要性从「agent 需要记忆」理论推出，再推出「所以要图」，起点是假设，后面精雕（关系/折叠/焦点）填不上起点空洞。

### 2. 症结：LLM 上下文窗口本身就是记忆

- 上下文窗口是 LLM 最自然的记忆形态；cu 之所以简单，是把记忆外包给上下文窗口，让 LLM 自己组织。
- 认知图必要性不在「抽象需要记忆」，在上下文窗口的局限：有限（装不下）/ 贵（每次重拼）/ 不持久（跨 cu、跨会话丢）。
- 只有撞上这三个局限之一、产生具体疼痛，图才从「抽象需要」变「具体必需」。

## 二、方向修正

### 3. 认知图可能不是「预先设计的第三件」，而是「cu 跑起来后长出来的」

- 对齐 checkpoint-8「好奇不设计」：不该先画好图，该先让 cu + lm-service 跑通最小 agent（纯上下文），跑起来观察哪里真卡，卡点才是图该有的形态。

### 4. 之前图设计是「预研」非「必须现在实现」

- 关系类型 / 四通道 / 图无决策 / 情绪还原 = 图一旦长出来该长什么样的预研，不往前推为必须实现的第三件。

### 5. 可执行验证方向

- 先跑无图最小 agent（纯上下文），专挑「必须跨 cu 记住、但上下文装不下/丢了」的具体任务去撞，撞出疼痛再回头看图怎么长。

## 待决

- 继续「先想清楚图再实现」 vs 「先跑无图最小 agent，让图从痛点长出」。
