- MVP = **4K 上下文聊天机器人**（用 cog-runtime 实现）。上下文硬限制（4K 举例），所以记忆一开始就必要（不是「跨 cu 才需要」）。

## 二、记忆先不用图，用文件组织

```
agent 目录/
  profile.md    # replace：锚点 + 印象（当前上下文单份落盘）
  events.log    # append-only：日志旁路，分析用，不回流
```

- 每次 LLM 上下文总是落盘，只保留一份（replace）；历史在日志（append）。
- 智能每次是改写，不是 append 保真；不漂移靠锚点，不靠留全历史。

## 三、两个工具（LLM 视角的能力）

### 工具1 — LLM 自己组织上下文

- 入参 = 下次运行的上下文（LLM 是上下文内容的唯一作者）。
- 提供基本锚点：上下文中有一份信息**位置永不丢**（程序保证拼入，不被挤掉），防迷失；内容可被 LLM 更新。

### 工具2 — 存取信息（id 隔离文件系统）

- 存：内容 → id（不是文件路径）；取：id → 内容。
- **读后失效**（id 一次性，读完即焚）；文件大小 ≤4K；内容太多存多个文件；上下文由 LLM 自己重组。
- 底层 append-only、不可覆盖；「改写」= LLM 写新 id、下次上下文改引新 id（旧内容还在底层）。

## 四、预算控制（最终定稿）

- **软预算 + 冗余**：名义 4K，实际预留更长（如 32K），不硬截断（截断不可取，会砍尾丢重要信息）。
- **每轮程序检查**：lm-service 返回即有实际 token 数，程序判断是否超 4K。
- **超了 → 注入指令整理上下文**：整理时**暂停思考**，整理完继续 → 不影响 LLM 思考的流畅度。
- 4K 是程序给的容器，不是 LLM 自觉守的线；程序管大小，LLM 管取舍。

## 五、关键边界（本会话确立）

- **主 cu 无容量感知**：主 cu 上下文里没有「4K」概念，不知道超没超；「超限」元信息只进整理 cu 的 prompt，不进主 cu。
- **主 cu 无历史感**：主 cu 只有一份「现在」上下文，无快照、无对照，看不到「被改」的痕迹（被改写需两份对照才可见，它只有一份）。历史痕迹全在日志旁路。
- 因此「主 cu 会不会困惑」「主 cu 会不会学会不超」都是伪问题：它无从感知。

## 六、核心结论：预算外包，取舍自学

- **控长度不是智能，是机制**：预算控制外包给程序（检测）+ 整理 cu（注入指令整理）。
- **会取舍才是智能**：留什么、丢什么、把什么拆出去存文件，归 LLM（语义层）。
- 让 LLM「自学适应超限」不可取：会把守预算的焦虑前置到表达阶段，主动写短/丢细节，降低质量。外包预算，才让主 cu 放心表达，压缩由事后整理承担。
- 混乱感（人的方式）是下一层议题，暂不展开；MVP 先落「检测超限 → 注入整理指令」这条机制。
