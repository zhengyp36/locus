# checkpoint-9 — 修正 cu 表述 + 两层并发正交 + ce 优先级调度

## 当前问题

复述 lm-service / cog-unit 职责时，把 cu 说成「管内容/会想」，与 checkpoint-7 原文「cu 只做格式/模板组织（填告知值），不含选什么」冲突；并发单边归给 lm-service，模糊了 ce 调度职责。

## 关键结论（YZ 澄清）

### 语义边界修正

- **语义 = 上层业务/cog-func**：决定跑什么、拆成什么 cu、每个 cu 装什么内容、选哪些片段。
- **cu/ce = 纯机制**，不管语义：
  - cu = 组装：把上层给好的内容按模板填成 prompt（心智现场）+ 结果写回树。
  - ce = 调度：依赖就绪判断、优先级、并发窗口、预算/停条件安全阀。

### 两层并发正交

| 层 | 并发是什么 | 有无优先级/依赖意识 |
|---|---|---|
| lm-service | 物理限流闸门：不超厂商并发数，尽量提高吞吐 | 无。上游丢多少接多少，超了才内部排队 |
| ce | 逻辑调度：无依赖 cu 并发、依赖未就绪等着、按优先级抢占 | 有。只有它知道「谁该先跑」 |

- 调度必须放 ce：优先级/依赖只有 ce 知道，lm-service 故意不知道全局。
- 带优先级进 lm-service 会把无脑层复杂化，违背「裸盘 IO」定位。
- lm-service 无队列是自然结果（除非 cu 瞬时超厂商并发数），非额外设计。

### 通用控制模式

「无脑执行层 + 有脑调度层」分离 = OS「调度器 vs 设备驱动」/ 队列「dispatcher vs worker」同构。有脑层必须卡在无脑层前面：ce 是 lm-service 上游闸门，lm-service 只做下游物理保护。

## 遗留 / 待想清

- ce 优先级的具体策略（抢占/权重/饥饿防护）待定，属机制层可后置。
- 其余 checkpoint-7 遗留（卸载/加载、意识层定位、cu 最小契约、输入侧主动管理）仍开。
